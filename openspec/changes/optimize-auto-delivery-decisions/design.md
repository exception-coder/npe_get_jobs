## Context

自动投递当前把所有岗位结果直接渲染在一个列表，并且每次运行都重新请求模型。现有 `RecruitmentIntentMatchEntity` 已保存岗位匹配证据，但缺少置信度和完整判定上下文，无法安全复用。变更跨越 Vue 工作区、自动投递 API、Java 匹配编排和持久化模型。

实现坐标以当前源码和 Git diff 为准：`TodayAutoDelivery.vue`、`RecruitmentJobSelectionService`、`RecruitmentMatchEvidenceService`、`RecruitmentIntentMatcher` 和 `recruitment_intent_match.sql`。Graphify 本次不可用，未将其作为证据。

## Goals / Non-Goals

**Goals:**

- 将大量检查结果按业务结论分组并限制初始 DOM 数量。
- 让每条结论可追溯到原 JD，并展示判定置信度。
- 安全复用输入未变化的高置信度明确拒绝，避免重复模型调用。
- 允许用户为缺失信息提供持久化的补充判定规则。

**Non-Goals:**

- 不缓存“投递”或“无法判定”结论。
- 允许用户规则明确豁免学历、经验等维度，但不覆盖岗位方向或明确排除职位。
- 不实现服务端结果分页、变更发送确认或送达回执语义。

## Decisions

### 真实联系确认是文字发送的唯一开关

Java 已在单岗位和自动投递入口完成显式确认，发往 sidecar 的 `confirmContact=true` 是统一的副作用授权。Node 不再额外读取附件选项中的 `sendGreeting` 决定是否发送，避免旧默认值把已确认操作降级成草稿；发送后仍要求输入框清空和新增送达/已读回执，失败不记录成功。

BOSS 发送前先在当前会话内选择唯一可见、启用的发送控件（已知 `.btn-send` 或语义明确的“发送”按钮），没有按钮时在有限等待后明确失败，不猜测 Enter。动作执行前再次核验收件人及草稿，并落盘提交阶段；执行后等待草稿清空及新增目标文字的送达/已读回执。草稿未及时清空不能证明未发送，因此不在动作后切换控件再次提交。

自动批次不再直接从 `startFromJob` 跳到 `confirmContact`。它与岗位库单岗位投递一致，先执行只读的 `prepareContact` 并要求目标岗位返回 `READY`，再进入确认发送；未就绪的入口逐岗位记录失败，不触发发送副作用。

### BOSS 地区只落到城市级

地区字典仍允许用区县名称反查父城市，例如“安溪”解析为泉州城市编码，但搜索 URL 构造器不接受或输出 `areaBusiness`。双层约束同时防止新解析结果和历史调用参数把搜索重新收窄到具体区县。

### 候选范围以未投递状态为准

候选查询按平台筛选未删除、未成功联系的岗位，并保留 500 条批次上限，不再使用创建或更新时间作为准入条件。历史明确拒绝仍由匹配证据缓存识别并跳过；相比先按日期截断，这能让旧的未判定岗位重新进入当前意向的判断流程，同时避免把已投递岗位加载进批次。

### 分组组件按批次扩展 DOM

为每个分组创建独立组件，默认渲染 20 条，用户点击后每次增加 20 条。相比一次渲染全部结果，这直接限制页面节点数量；相比服务端分页，它保留现有轮询响应协议，部署风险更低。当前单次岗位上限为 500，若未来突破该边界再引入游标接口。

### 只复用高置信度明确拒绝

缓存键由 `platform + platformJobId + JD hash + intent version + decision context hash` 组成。判定上下文包含用户补充规则；任何会影响结论的输入变化都会失效。只复用 `skip` 且高置信度的证据，因为错误复用“投递”会造成实际外发风险，错误复用不确定结论则会阻止信息补全后的重新判断。

候选替代方案是按岗位 ID 永久标记拒绝，但 JD、求职意向或规则更新后会产生陈旧结论，因此不采用。

### 用户规则作为受约束的模型输入

补充规则作为独立数据段进入匹配提示词。用户可明确豁免学历、经验、地域或薪资等准入维度；模型必须逐字引用该规则作为证据，后端同时核验引用确实存在。岗位方向和明确排除职位只能由 JD 证据判断，不能被补充规则覆盖。长度限制 2000 字，前端在当前浏览器持久化，后端再次校验长度，避免绕过 UI。

### 增量扩展现有证据表

在 `recruitment_intent_match` 增加 `confidence` 和 `decision_context`，并建立缓存查询组合索引。旧记录分别使用 `low` 和 `legacy` 默认值，因此不会被误当成可复用证据。应用沿用 Hibernate schema update 自动演进，不登记人工执行 SQL。

## Risks / Trade-offs

- [模型置信度是离散标签，不是校准概率] → 仅将最高级别用于拒绝缓存，并把判定原因与原 JD 同时提供给用户复核。
- [响应仍携带全部结果，极大数据量仍有网络成本] → 当前限制 500 个岗位且 UI 限制 DOM；后续超出边界时另行设计服务端分页。
- [JD 文本细微变化导致缓存失效] → 接受重新判定以优先保证正确性，使用稳定 SHA-256 指纹避免内容误匹配。
- [Hibernate 自动更新在不同数据库环境行为有差异] → 保留基线 DDL 和 SQLite 映射回归；本次 DDL 权威证据状态为未核验。

## Migration Plan

1. 部署包含实体字段、索引和查询逻辑的 Java 服务，由现有 schema update 增加列。
2. 部署前端资源；旧证据因默认低置信度与 legacy 上下文自然失效。
3. 验证 Java 全量测试、Node 全量测试、真实 Vite 浏览器场景和生产构建。
4. 若需回滚，回退应用提交即可；新增列和索引可保留，不影响旧版本读取既有列。

## 匹配过度保守修复

用户提供的批次反馈为 202 个候选、67 个已检查、0 个成功；本次源码核对确认：缺失检查在强度判断前设置全局 unknown，使 prefer 也阻断；空 description 完全绕过模型；原文引用与 JSON 序列化字符串直接比较，真实换行和引号会被转义。批次统计来自用户反馈，未作为本机数据库重现结果。

`IntentMatchResult.decide` 继续归一化全部检查，但只将职位方向缺失归为 review。任何有可信证据的非 prefer 冲突仍为 skip；职位符合且其他字段 unknown 为 apply、medium，保留 unknown 与提示，不将未知伪装为符合。prefer 缺失或不符合不改变准入。

`RecruitmentIntentMatcher` 从职位、公司、城市、薪资、正文和 facts 的实际值建立证据候选，按连续原文片段核验；仅统一 Unicode 排版形式和空白，不做相似度推断。平台 ID、URL、历史结论不作为岗位内容证据。无正文仍调用模型；空职位或超长输入继续保守回退。提示词明确优先行业不是准入条件，未写限制不是明确冲突。

对明确 `CNY/month` 意向与可识别 K 月薪，领域规则确定区间是否重叠，避免模型把 10–25K 与 20–40K 判为冲突。年/月单位缺换算依据不推算；经过证据验证的用户薪资豁免保留。判定缓存上下文加入策略版本，旧严格策略生成的 skip 不被复用，无需删除历史记录或变更 DDL。

匹配修复切片复用意向卡、AI 匹配、匹配缓存、岗位选择、自动投递和工作流 JUnit 套件，覆盖未知放行、硬性拒绝、虚构证据、结构化岗位、空白引用、薪资交集及缓存失效。自动投递调用使用 mock，不向招聘平台发送消息；该切片仅修改 Java 匹配规则。

## BOSS 草稿、发送与防重修复

用户反馈的四例为两例发送入口不可用、一例草稿校验失败、一例尝试日志防重。源码确认严格 `innerText` 比较、动作后按编辑器状态切换发送手段、入口前的永久尝试预占；本机无这四例的原始 journal，也无可访问的真实 BOSS 聊天页，因此不将历史日志统计当成已重现。

草稿原子能力同时供聊天页和 `fillBossDraft` 使用：读取 value/渲染文本，统一 CRLF、NBSP、零宽占位及末尾空行；保留正文空格与段落差异。已有不同草稿不覆盖，相同草稿复用；新正文统一点击聚焦后通过 keyboard.type 逐字输入，任何草稿操作均不按 Enter。

发送能力先校验唯一编辑器、目标文字及收件人，再解析当前会话内的发送动作。按钮探测独立为 focused capability，每轮重新读取当前可见控件及禁用状态，在有限时间内容忍延迟挂载、替换和启用；多个候选明确失败，缺控件不回退 Enter。按钮不带旧 class 时使用明确 button/role 语义。执行一个选定动作后只观察回执，不补发第二次。回执必须是目标文字旁独立的“送达/已读”状态，“未送达”和其他消息的回执不能作为依据；编辑器缺失不能当成清空。预校验错误保留具体原因，已执行动作但没有回执才标记不确定。

持久化 journal 增加阶段与 `entryAttempted/textAttempted/imageAttempted` 标记，提交前原子写入；独立锁文件保护进程间并发，内存锁保护同页并发。入口点击可能已产生平台副作用，因此入口状态未知继续阻断。已核验会话且明确没有提交文字/图片的草稿失败或草稿保存，可从聊天页继续，不能再次点击岗位“立即沟通”。旧记录仅明确的草稿失败/草稿保存且会话已建立、无文字/图片送达时允许恢复；旧未知状态不自动清除。成功或可能已提交的记录继续防重。异常退出残留锁不通过超时自动绕过。

实现按草稿、发送、journal 与联系编排分离，复用现有 BOSS 身份校验。修订 sidecar health revision 并同步 Java 消费者，防止旧 Node 服务仍被当成可用。用全部请求拦截的 Patchright 浏览器夹具及临时 journal 目录验证单次提交、延迟回执、多行草稿、会话变化、并发、防重和安全恢复；禁止真实平台发送。

## 编辑器就绪与联系人定位补齐

源码证明原先只核对编辑器文字；文字一致时不会检查按钮是否已接受输入，800ms 内未启用即失败。Patchright 自带类型文档明确 `fill` 会触发 input，因此不把用户截图中的“fill 一定不触发 input”作为已证实根因。新增回归模拟文字可见但依赖键盘事件的状态未更新，以及按钮晚于初次探测才挂载的场景。

草稿初次输入与一次刷新复用原生键盘能力，当前会话中存在禁用发送控件时，只对仍为空或仍等于目标文字的编辑器刷新。选区限制在编辑器内，逐字输入保持多行，不按 Enter；再验证正文与控件状态。不同草稿继续保护。草稿准备返回就绪状态，不能把 `draftFilled` 当成已发送或按钮可用；正式发送另行复核。

联系人定位移入独立模块。先验证当前会话，正确时无需依赖侧栏是否渲染；否则按精确招聘者姓名查找，优先使用同 name-box 的公司证据。公司标签在外层且姓名唯一时可先选择，但必须在当前会话重新核对公司、职位、招聘者后才能写草稿。重复姓名缺少唯一公司依据时阻断。未找到目标时只滚动 name-box 的最近可滚动祖先，排除 body、html 及聊天正文，最多八次并限制总等待；不扫描或修改框架私有 store，不凭空构造平台 API。

journal 不批量删除历史失败、不靠时间放开重试；旧版按钮不可用记录还必须显式证明文字和图片均未尝试提交，才能恢复。同时拒绝文字或图片尝试标记与草稿原因冲突的旧记录。预提交失败保留可恢复阶段；新旧成功、提交未知、入口未知、锁定记录仍阻断。回退代码不清除 journal。

真实 Chrome 消息页本次重定向登录页；用户随后明确交由测试人员完成真实验收，因此本轮自动回归仅访问拦截的本地夹具和临时日志，不宣称已通过真实 BOSS 编辑器验收，也不执行真实发送。

## 原生键盘输入与预占误锁修复

2026-10-21 用户反馈四例按钮不可用、六例防重；当前环境没有这十例原始 journal，不能将统计当作本机复现，也不采纳未经核实的 React 框架归因。代码确认上一轮刷新仍调用 insertText，方向键不能证明应用收到了正文编辑按键。新增夹具只在正文编辑键结束后更新发送状态，以区分单次 input/方向键与真实文本键盘周期。

初次与刷新均点击编辑器、检查其现有正文，再通过 keyboard.type 逐字输入。隔离浏览器证明 type 直接收到换行会发送 Enter，不能把整段多行正文传入：正文片段使用 type，仅换行和 Tab 分隔符使用 insertText，其他控制字符拒绝。中文在 Chromium 中可能通过文本插入实现而不产生字母键事件，因此用一次临时空格和 Backspace 完成正文编辑按键周期：只在读回恰为目标正文加一个空格时删除该空格；若长度限制拒绝空格则不删除真实正文，若出现其他变化则停止。正文最终仍须严格核对；输入不合预期不盲目重写。

另一处代码缺口是先写 TEXT_SUBMITTING，再复核身份、草稿与按钮；后续预检失败即使从未调用 click，也会留在不确定阶段。将最终预检与 click 调用明确分界：只有前者失败才调用 onNotSubmitted，原子恢复 DRAFT_READY/textAttempted=false 并清除不确定原因；click 一旦调用、超时或没有回执，绝不执行该恢复。日志仅在原子写入成功后发布内存状态，恢复日志写失败仍保持不确定记录，避免最终结果写回错误地带入未持久化的恢复。历史六例未经平台核对不自动解锁；新版准备失败可恢复路径另用持久化回归证明。

修订 health 为新版本并同步 Java 消费者；自动回归全部拦截网络、使用临时日志，真实平台验收继续交由测试人员，不执行真实发送。
