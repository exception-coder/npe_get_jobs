## Context

自动投递当前把所有岗位结果直接渲染在一个列表，并且每次运行都重新请求模型。现有 `RecruitmentIntentMatchEntity` 已保存岗位匹配证据，但缺少置信度和完整判定上下文，无法安全复用。变更跨越 Vue 工作区、自动投递 API、Java 匹配编排和持久化模型。

实现坐标以当前源码和 Git diff 为准：`TodayAutoDelivery.vue`、`RecruitmentJobSelectionService`、`RecruitmentMatchEvidenceService`、`RecruitmentIntentMatcher` 和 `recruitment_intent_match.sql`。Graphify 本次不可用，未将其作为证据。

## Goals / Non-Goals

**Goals:**

- 将大量检查结果按业务结论分组并限制初始 DOM 数量。
- 让每条结论可追溯到原 JD，并展示判定置信度。
- 安全复用输入未变化的高置信度明确拒绝，避免重复模型调用。
- 允许用户为缺失信息提供持久化的补充判定规则。

**Non-Goals:**

- 不缓存“投递”或“无法判定”结论。
- 允许用户规则明确豁免学历、经验等维度，但不覆盖岗位方向或明确排除职位。
- 不实现服务端结果分页、变更发送确认或送达回执语义。

## Decisions

### 候选范围以未投递状态为准

候选查询按平台筛选未删除、未成功联系的岗位，并保留 500 条批次上限，不再使用创建或更新时间作为准入条件。历史明确拒绝仍由匹配证据缓存识别并跳过；相比先按日期截断，这能让旧的未判定岗位重新进入当前意向的判断流程，同时避免把已投递岗位加载进批次。

### 分组组件按批次扩展 DOM

为每个分组创建独立组件，默认渲染 20 条，用户点击后每次增加 20 条。相比一次渲染全部结果，这直接限制页面节点数量；相比服务端分页，它保留现有轮询响应协议，部署风险更低。当前单次岗位上限为 500，若未来突破该边界再引入游标接口。

### 只复用高置信度明确拒绝

缓存键由 `platform + platformJobId + JD hash + intent version + decision context hash` 组成。判定上下文包含用户补充规则；任何会影响结论的输入变化都会失效。只复用 `skip` 且高置信度的证据，因为错误复用“投递”会造成实际外发风险，错误复用不确定结论则会阻止信息补全后的重新判断。

候选替代方案是按岗位 ID 永久标记拒绝，但 JD、求职意向或规则更新后会产生陈旧结论，因此不采用。

### 用户规则作为受约束的模型输入

补充规则作为独立数据段进入匹配提示词。用户可明确豁免学历、经验、地域或薪资等准入维度；模型必须逐字引用该规则作为证据，后端同时核验引用确实存在。岗位方向和明确排除职位只能由 JD 证据判断，不能被补充规则覆盖。长度限制 2000 字，前端在当前浏览器持久化，后端再次校验长度，避免绕过 UI。

### 增量扩展现有证据表

在 `recruitment_intent_match` 增加 `confidence` 和 `decision_context`，并建立缓存查询组合索引。旧记录分别使用 `low` 和 `legacy` 默认值，因此不会被误当成可复用证据。应用沿用 Hibernate schema update 自动演进，不登记人工执行 SQL。

## Risks / Trade-offs

- [模型置信度是离散标签，不是校准概率] → 仅将最高级别用于拒绝缓存，并把判定原因与原 JD 同时提供给用户复核。
- [响应仍携带全部结果，极大数据量仍有网络成本] → 当前限制 500 个岗位且 UI 限制 DOM；后续超出边界时另行设计服务端分页。
- [JD 文本细微变化导致缓存失效] → 接受重新判定以优先保证正确性，使用稳定 SHA-256 指纹避免内容误匹配。
- [Hibernate 自动更新在不同数据库环境行为有差异] → 保留基线 DDL 和 SQLite 映射回归；本次 DDL 权威证据状态为未核验。

## Migration Plan

1. 部署包含实体字段、索引和查询逻辑的 Java 服务，由现有 schema update 增加列。
2. 部署前端资源；旧证据因默认低置信度与 legacy 上下文自然失效。
3. 验证 Java 全量测试、Node 全量测试、真实 Vite 浏览器场景和生产构建。
4. 若需回滚，回退应用提交即可；新增列和索引可保留，不影响旧版本读取既有列。
